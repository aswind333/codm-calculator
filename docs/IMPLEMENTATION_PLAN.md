# CODM 抽奖概率与成本计算器 — 开发实施计划（IMPLEMENTATION_PLAN）

- **版本**：v1.0（2026-11-17）
- **项目目录**：`~/codm-calculator/`
- **项目阶段**：需求与设计已完成；程序尚未按这些需求实现
- **开发主体**：用户 + ChatGPT（需求澄清、规格与验收审查）+ VS Code Codex（按阶段编码、运行测试、报告结果）
- **首版交付物**：可在 Windows / macOS / Android / iOS 主流浏览器使用的简体中文、响应式、纯前端静态网站
- **部署目标**：个人 GitHub 仓库保存代码；经用户批准后，以 Cloudflare Pages 免费静态托管发布
- **重要边界**：**此文件是执行计划，不授权 Codex 一次完成全部阶段，更不授权自动推送代码或部署上线。**

## 0. 计划依据、优先级及已知冲突

本计划依据以下**已经完成的项目文件**编制；Codex 开工前必须实际读取这些文件，不可凭聊天摘要代替：

2. `docs/PROBABILITY_SPEC.md` **v0.1**：默认概率、剔除式计算、成本与等效卡片数公式、数值精度、T-01～T-10 数学测试。

4. 本文件：**执行顺序、允许的改动范围、各阶段验收、Codex 交接方式**；它不能修改上面已确认的产品或数学规则。

**职责优先规则**：产品行为和首版范围遵循最新 `PRD.md`；数值算法和异常边界遵循 `PROBABILITY_SPEC.md`；样式、交互呈现遵循 `UI_DESIGN.md`；本文件规定如何实施。若职责范围内仍有实质冲突，Codex 必须记录冲突并停止相关实现，不能擅自选一个版本。

**已识别的旧文字差异**（S0 应检查并记录；它们不构成重新讨论需求的理由）：

- `PROBABILITY_SPEC.md` §6.3 曾允许“编辑概率或价格后即时重新计算”。该表述仅可理解为**计算页已生效配置或勾选状态变化时立即刷新**；**设置页面的未保存草稿不得影响计算页**，以 `PRD.md` v0.3 FR-05-C 为准。

- 数学规格 §11 和 UI 规格 §12 仍包含对旧 PRD v0.2 的历史引用；以已确认的 v0.3 作为现行功能基准，不自行重写数学定义。

## 1. 技术方案与实现原则

### 1.1 沿用现有项目，不重新搭脚手架

用户已经创建 `~/codm-calculator`，使用 **React + TypeScript + Vite** 模板并选用 **Oxlint**；`npm run dev` 已成功启动 Vite。**Codex 不得在现有目录上重新执行 `npm create vite`，也不应擅自改用 Next.js、Vue、Flutter 或重量级后端框架。**

| 领域 | 首版建议方案 | 理由/限制 |
|---|---|---|
| UI 与语言 | React + TypeScript | 保持现有技术栈，编写静态前端 |
| 开发与构建 | 现有 Vite + npm | 沿用 `package.json`、`package-lock.json` |
| 静态检查 | 现有 Oxlint + TypeScript 类型检查 | 不要仅凭 Vite 能启动就认为类型正确 |
| 核心数学测试 | Vitest | 适合纯 TypeScript 函数单元测试 |
| React 交互测试 | React Testing Library + user-event | 用用户点击、输入、保存等行为验收 |
| 端到端测试 | Playwright（在后期引入） | 覆盖主要浏览器和移动视口，避免过早增加复杂度 |
| 样式 | CSS 变量（Design Tokens）+ 响应式 CSS | 小清新主题可集中换肤，首版不必上复杂设计系统 |
| 图标 | Lucide 或本地 SVG | 一、二、三等奖图标与顶部入口 |
| 设置持久化 | **建议首版使用 `localStorage` + 独立存储适配层** | 数据只有 8 类小配置；保持无后端、易测试；若实测出现需求再换 IndexedDB |
| 发布 | GitHub + Cloudflare Pages 静态站 | `npm run build` 生成 `dist/`，无服务端运行时 |

**说明**：上述 Vitest / Testing Library / Playwright / `localStorage` 属于**本实施计划提出的技术选择**，并非用户之前逐项钦定；允许 Codex 在 S0 提出有依据的等价替代，但**需先经用户确认**，不得自行大幅换栈。初版不必同时引入多个 UI 库；只有在真实需要时，再选择轻量组件/动画依赖。

### 1.2 关键架构边界

```text
内置默认模板（独立、不可被用户编辑数据覆盖）
             ↓
已保存生效的配置 ←——【显式保存/校验】—— 设置页面草稿
             ↓
奖品已抽状态（按 typeId 隔离）
             ↓
纯函数计算引擎（概率 / 卡片费用 / 单轮等效成本）
             ↓
React 展示（计算主页 / 结果表）

本地持久化适配层：配置数据、已抽状态分别持久化；
核心计算模块不直接访问 localStorage / DOM / React / 网络。
```

建议分离以下职责，**具体文件名由 S0 的现有目录检查后决定**：

- `src/domain/`：类型、配置校验、概率与花费纯函数、格式化函数。
- `src/data/`：8类默认转盘与稳定的 `typeId`、`prizeId`。
- `src/features/calculator/`：类型选择、已抽集合、费用摘要、奖品网格、结果表。
- `src/features/settings/`：价格矩阵、概率卡片、草稿编辑、保存/取消/重置。
- `src/features/rules/`：使用步骤、七/十抽示例、FAQ。
- `src/storage/`：版本化本地读写、校验与故障处理。
- `src/styles/`：主题变量及共用样式；测试可就近放 `*.test.ts(x)`。

不要因为上面的建议而预先创建大量空目录；实现到对应阶段再建立。

### 1.3 数据和状态的基本约束

- 内置**8类**：7类十抽（传说载具、传说近战、传说载具+武器、传说武器、神话武器、传说角色、神话角色）+ 1类七抽通用，默认概率和价格**逐项照搬数学规格 §2**，不自行改值。
- 对每类保留稳定 `typeId`，对奖品保留稳定 `prizeId`；可修改展示名称，不可因改名更换 ID。
- 已抽集合和每类已保存参数隔离；用户点击奖品**立即改变当前已抽状态**，这不属于“设置自动保存”；**价格、初始概率、名称、单位必须点「保存设置」才提交**。
- 建议设置数据与已抽记录使用**不同的版本化存储键**，例如 `codmcalc.settings.v1` 与 `codmcalc.drawn.v1`；不应把未保存的草稿写入正式设置存储键。
- **保存原子性**：先校验、序列化并成功写入本地存储，再更新应用中的“已保存配置”与成功提示；存储失败时旧有效配置仍生效、草稿保留并可重试。
- 本地读取的数据视为**不可信输入**；版本错误、JSON 损坏、奖品 ID 不合法或参数不通过校验时，不能传给概率引擎；优先安全回退默认模板并给出可理解的提示。
- 零权重奖品、非法/缺失价格、总剩余权重为0等特殊状态按数学规格处理，不能出现 `NaN` / `Infinity` 冒充正常结果。
- 首版文案使用简体中文；可集中维护，但不强制提前引入 i18n 框架。

## 2. Codex 协作协议（所有阶段都必须遵守）

### 2.1 一次只执行一个阶段

1. 用户在 VS Code 打开已信任的项目根目录，进入 Codex 面板。
2. 每次指定 **一个阶段编号（S0～S7）**；Codex 先读本文件对应阶段、相关规格和实际项目代码。
3. Codex 在该阶段内自行完成合理的小步骤：检查 → 修改 → 运行测试 → 修复本阶段问题 → 报告。
4. **结束后停在阶段边界**，不得未经用户同意自动开始下一阶段；用户复核后再继续。
5. 对重大需求冲突、不可逆操作、平台登录、代码远程推送、网站上线等须先请求用户明确批准。

这是一种**按阶段交付、人工设置验收关卡**的方式，不要求用户每敲一行代码都批准，也不允许 Codex 一次改完所有页面而没有中途验证。

### 2.2 每次 Codex 汇报格式

每个阶段的最终汇报至少包括：

1. **完成内容**：对应哪些 FR/AC/T 编号。
2. **改动文件**：新建/修改/删除文件清单及关键原因。
3. **实测命令**：逐条写出运行了什么、通过/失败、必要的错误摘要（不得只说“应该能通过”）。
4. **人工验收方法**：提供 `localhost` 页面路径及 2～5 个具体可重现的操作步骤；无法自动验证的部分如实说明。
5. **剩余问题**：明确问题、严重度、规避方式；没有则写“无已知阻塞”。
6. **阶段结果**：`PASS` / `BLOCKED`，**停止并等待下一阶段指令**。

可在项目中维护一个简短 `docs/DEV_LOG.md` 记录阶段结果和重要决策（S0 创建），**不要把日志伪装成需求文档**。

### 2.3 修改与安全范围

- 工作区限定当前 `codm-calculator/`，尊重现有文件；修改前检查 `git status`，**不覆盖不属于本阶段的用户改动**。
- 依赖只通过 npm 正常安装；说明新增依赖的用途，优先选择少量成熟的工具。不要为了美化引入大型3D引擎。
- 不提交密钥、令牌、真实账号数据、`node_modules/`、`dist/` 或本地浏览器数据；检查 `.gitignore`。
- 不擅自进行 `git push`、创建远程仓库、连接 Cloudflare、配置域名或开启计费；这些放到 S7，由用户明确授权。
- 本地 Git commit 可以作为阶段存档，但应先向用户说明拟提交内容；不能擅自重写历史或使用破坏性的 Git 命令。
- **不得以删除测试、关闭类型检查、放松约束或静默改动需求文档的方式，让失败检查“变绿”。**
- 若需要改动产品决策：先写出“现行要求—发现的问题—建议修改—影响范围”，等待用户确认后再更新规格。

### 2.4 统一质量门槛

从引入相关脚本后，阶段交付时至少运行适用项：

```bash
npm run lint
npm run typecheck
npm run test
npm run build
```

- S0 先检查现有 `package.json`，命令**以实际脚本为准**；若 `typecheck` / `test` 不存在，由 S1 建立，不能谎称已执行。
- 建议 `test` 对应 **Vitest 单次运行**（非持续 watch），另设 `test:watch`；`typecheck` 调用适用的 `tsc` 命令，`build` 沿用 Vite 项目脚本。
- **验收门槛**：测试绿灯 + 构建成功 + 关键 UI 操作可演示 + 需求无无声偏离。若任何必要检查失败，阶段不得标为 PASS。
- 端到端 / 视觉验证从 S6 逐步加上；**测试截图属于辅证，不能替代核心算法断言**。

## 3. 逐阶段实施路线（S0～S7）

### S0 — 代码仓库审计与开发基线（只检查和整理，不开始功能开发）

**目标**：确认 Mac 上现有 Vite 项目实际状况，使 Codex 理解三份规格、发现冲突并建立可复现的起点。

**执行范围**：

- 读取 `docs/PRD.md` v0.3、`docs/PROBABILITY_SPEC.md` v0.1、`docs/UI_DESIGN.md` v1.0 和本计划；确认它们位于项目内、内容与版本一致。
- 审核当前 `package.json` / 锁文件、Node 和 npm 版本、Vite、React、TS、Oxlint、`src/`、`.gitignore`、当前 Git 状态；**沿用用户刚创建的项目，不重建模板**。
- 运行当前已存在的 `npm run build`、`npm run lint`（如有）及 `npm run dev`，记录结果；不强行假设所有脚本已经存在。
- 以本计划 §0 为基础整理**简短冲突/待处理清单**；确认三份文档的要求能实施。
- 建立（或建议建立）`docs/DEV_LOG.md`；根目录 `AGENTS.md` 留到用户批准后单独生成，保持简短，引用文档而非复制几十页规格。
- 若项目没有初始化 Git，先报告状态并提出本地初始化建议；**不要直接建立远程仓库或推送**。

**验收证据**：可复现的本地运行结果、项目版本清单、没有遗漏的关键规格、建议的项目结构、当前 Git 状态；没有改动用户需求或大规模源代码。

**阶段停止点**：用户确认 S0 结果，才执行 S1。

### S1 — 类型、默认配置、数据校验与测试基础

**目标**：先把数据源固定，再写概率算法；避免 UI 中散落不同的价格数字。

**执行范围**：

- 按数学规格 §2 实现 8 类转盘**单一默认数据源**，含稳定类型 ID、奖品 ID、7/10 数量、权重、逐轮费用、名称及单位；每类必须返回**独立的可编辑副本**，不可误共享可变数组。
- 实现静态类型与基础配置校验：数量、唯一 ID、初始概率有限且非负且总计100（数学规格容差）、价格有限非负整数、名称/单位有效性。
- 安装配置 Vitest，添加 `npm run test`、`npm run test:watch`，明确类型检查脚本；尊重已经选用的 Oxlint。
- 将默认数据测试做成**表驱动测试**，覆盖 8 类价格数组逐项一致、总价 `538 / 538 / 888 / 888 / 1008 / 1008 / 1448 / 698`、七抽只有7项、七抽/十抽权重总和100。
- 提供设置恢复默认时可复用的纯函数（**仅负责复制模板，不实现设置页面**）。

**验收（主要对应 AC-01～04、T-01、T-06）**：

- 8 类数据完整且可独立修改副本；共享的出厂常量不变。
- 有效/无效配置的测试都通过；同总价但逐抽不同的转盘不会被合并。
- `lint`、`typecheck`、`test`、`build` 均通过。

**阶段停止点**：默认数据与校验测试通过后停止；不提前实现页面。

### S2 — 纯数学计算引擎与严格测试

**目标**：先证明计算正确，再把结果接入界面；避免 UI 逻辑“看起来对、实际算错”。

**执行范围**：

- 实现并导出 `getNextRound`、`calculateRemainingProbabilities`、`calculateCosts`、`calculateEquivalentCosts`、数值格式化等**纯函数**；可采用等价命名，但语义必须与数学规格一致。
- `p_i=w_i/Σ剩余w`；不放回剔除、任意已抽集合、轮次根据 `drawnIds.size` 推导；不得使用预设“第几抽固定概率表”。
- 等效卡片 `c/p` 使用未舍入概率；费用返回“此前已花费 / 本轮需要 / 完成本轮后累计 / 全抽总额”。
- 正确处理 `p=0`、剩余权重0、非法输入、已抽齐、最后一件正权重100%、免费0卡、空价格不是0、显示三位小数；禁止 NaN/Infinity 流入 UI。
- 写完并运行数学规格 **T-01～T-10** 的全部用例；包括十抽剔除6.5%和10%、七抽剔除60%等已核对的数值。
- **额外稳健性测试（仅测试，不作为首版“未来路径预览”产品功能）**：遍历默认十抽的1024种子集合和七抽的128种子集合，核查正权重剩余状态下概率总和≈1、概率在[0,1]、各输出有限；顺序无关。无需为此写用户界面的未来路径分析。

**验收（主要对应 AC-05～12、T-01～10）**：

- 所有数学断言通过，测试覆盖正常状态、异常状态和显示边界；核心模块无需浏览器、React 或存储即可测试。
- 特别核实：十抽第3抽二等奖 `1.497%` / `668.000`；七抽第2抽二等奖 `3.125%` / `224.000`；最后一抽100%。
- `lint`、`typecheck`、`test`、`build` 均通过。

**阶段停止点**：数学层通过审查后，才允许开始主界面。

### S3 — 概率计算主页面（首个可操作版本）

**目标**：用户能在浏览器中选择转盘、点击已抽奖品，立即得到完整准确的下一抽结果。

**执行范围**：

- 实现十抽 / 七抽模式与8种类型选择；按类型隔离已抽 `prizeId` 集合，切换回来仍能看见原类型的记录。
- 默认不提供单独轮次输入；根据已抽件数自动展示第几抽、已抽件数、本轮/累计费用。
- 卡片网格按一等奖至末等奖展示；前三等奖皇冠、奖章、星形；已抽状态有颜色变化、勾选及文字，可点击/键盘取消；提供「清空已抽记录」。
- 结果表**默认展示全部剩余奖品**，同列呈现下一抽真实概率与「本轮每100%概率等效卡片数」，统一三位小数，并固定说明该数字**不是保底或真实期望总成本**。
- 价格摘要至少显示：此前已花费、下一抽需要、完成本轮后累计、全部抽完总费用。
- 用 S2 的纯函数驱动界面，不把公式重复写在 React 组件里；完成状态/零权重错误有明确 UI。
- 先达到布局清晰可用，允许后期 S6 再精修高级配色、动画和所有尺寸；不做圆形转盘。

**验收（主要对应 FR-01～04，AC-05～16）**：

- 浏览器可复现国服核对案例：勾选六等奖与七等奖，得到第3抽一等奖 `0.096%`、二等奖 `1.497%` 等。
- 不同类型之间不串价格和已抽状态；所有剩余奖品均可见，摘要不混淆“此前”和“抽完本轮”。
- 至少用组件测试覆盖卡片勾选/撤销、类型切换、终局；自动化质量命令通过。

**阶段停止点**：由用户实际在 `localhost` 点击测试，确认主流程符合预期。

### S4 — 设置页、显式保存与本地持久化（最高交互风险）

**目标**：完成8类可配置价格/概率、草稿与已生效配置的严格隔离；保存后刷新仍生效。

**执行范围**：

- 设置页「抽奖价格 / 初始概率」两个标签，使用**同一份草稿**；桌面8行×最多10轮价格矩阵，七抽后3列「—」，合计动态更新；移动端逐类型编辑价格并可查看完整总表。
- 概率页可选8类，按7/10张小卡修改奖品名称、概率，概率合计实时显示；允许修改每类型卡片/CP单位标签。
- 保存/取消/重置（逐类价格、逐类概率、全部）只按 PRD 与 UI 规格执行：**编辑或恢复默认不自动生效；点击「保存设置」且整份草稿校验成功才生效**。
- 使用 `src/storage/` 隔离本地存储，建议版本化 `localStorage`；已抽状态可在主计算页变更时**独立持久化**，但绝不把“已抽自动更新”等同于“设置自动保存”。
- 保存流程：验证全部8类 → 序列化 → 写入成功 → 更新生效配置 → 展示成功；失败保留旧有效配置和用户草稿，报错明确。
- 支持「未保存修改」标志、取消编辑、站内离开确认、浏览器离开提醒（尽可能）；切换设置标签或转盘类型保留草稿。
- 存储加载遇到损坏 JSON、旧版本、非法配置或不可写时安全回退/报错，不直接使用脏数据；既存 ID 状态与奖品列表不匹配时清理并提示。
- 用户保存新概率后，如已抽状态落入零权重等不可能状态，遵循数学规格给出提示，不制造虚假的“已中奖概率”。

**验收（主要对应 FR-05，AC-17～20）**：

- 编辑 → **不保存** → 计算页结果不变；保存后结果改变，刷新浏览器仍保留修改。
- 无效数据保存失败且旧有效配置不变；逐类恢复默认只改变草稿，未保存的恢复操作不生效。
- 移动端与桌面端表单编辑相同数据；切换8类草稿不丢失；本地存储被模拟抛错时无虚假成功提示。
- 组件交互测试覆盖保存、取消、恢复、切页确认与数据隔离；所有质量命令通过。

**阶段停止点**：用户实际验证「修改 → 保存 → 刷新 → 恢复默认」，确认无误。

### S5 — 规则说明页与导航完整性

**目标**：新玩家无需看开发文档，也能读懂怎么使用、概率怎么变、性价比是什么意思。

**执行范围**：

- 完成全站顶部入口：可辨认的「规则说明」，右上角明显的粉紫齿轮「设置」，附近「可自定义概率」文本与轻微指向箭头；返回计算器操作明确。
- 规则页按已确认方案：三步教程；十抽/七抽切换计算示例（分别 `1.497%` / `3.125%`）；单轮性价比 `10 / 5%=200.000`；FAQ 可折叠；非官方声明与正确的服务器来源说明。
- 规则示例**与主计算状态隔离**：点选示例不能改变用户正在计算的转盘。
- 对键盘导航、按钮名称、FAQ 展开状态提供基本无障碍语义；说明页适当限宽。
- 可核对原始公开来源后添加对外链接，**不将 Garena 台服规则冒称国服官方公告**。

**验收（主要对应 FR-06～07，AC-14、AC-21）**：

- 三页相互可达、返回清晰；规则页示例切换数值正确且不影响主计算。
- FAQ 真实可操作；概率三位小数；性价比非保底说明显眼；各主要交互测试通过。

**阶段停止点**：用户阅读规则页，确认信息直观、文字没有误导。

### S6 — 视觉精修、响应式、无障碍与跨浏览器回归

**目标**：让“功能正确的网页”变成“手机与 PC 都真正好用、可发布的网页”。

**执行范围**：

- 按 UI 规格实现统一主题 CSS 变量：浅灰 `#F4F5F8`、粉紫 `#AA93E9`、适量浅蓝，白色内容卡；8类转盘不使用不同背景色；保持可读对比度。
- 窄屏手机（约375、430 px）、平板（约768 px）、桌面（约1280 px）检查，确保结果表可读、设置价格表局部滚动、手机有逐类编辑；不得出现全页面横向溢出或重要控件被遮挡。
- 轻量动画：卡片点击、数字变化、规则FAQ和设置箭头；支持 `prefers-reduced-motion`，在减少动画时停止非必要运动。
- 增加必要的 React 组件与**关键用户路径**端到端测试（建议使用 Playwright）：
  - 选择十抽、点六/七等奖 → 概率与花费正确；
  - 切换七抽 → 第二抽3.125%；
  - 修改价格/概率但不保存 → 主页面不变化；保存后刷新 → 生效；
  - 终局、清空、类型隔离、规则示例不污染主状态；
  - 移动端打开设置并能编辑七抽价格；
  - 减少动态效果下箭头不运动。
- 手工在 macOS Chrome 与 Safari 测试，条件允许时在真实 Android / iPhone 浏览器再测；自动化检查优先覆盖 Chromium 与 WebKit，必要时补 Firefox。
- 检查运行时不依赖远程字体、图标 CDN 或游戏服务器；控制初版图片和依赖体积，避免不必要的大包。
- 将所有已修复的实际问题补充为回归测试，避免后续改 UI 时算坏概率。

**验收（主要对应 AC-15、AC-17、AC-22～24）**：

- 用户能在手机和电脑完成完整流程；核心数据不被截断；无严重控制台错误和阻断性无障碍问题。
- `lint`、`typecheck`、`test`、`build` 及关键端到端测试通过；未验证平台/设备写明限制，不声称全面通过。
- 不存在首版范围外的模拟抽奖、未来路径预测或实际保底误导。

**阶段停止点**：用户批准进入发布前准备。

### S7 — 发布前审计、GitHub 与 Cloudflare Pages 部署（需逐项授权）

**目标**：在保持零后端与免费静态托管前提下发布首版，并可持续更新。

**执行范围**：

1. **发布前冻结检查**：对照 PRD AC-01～AC-24、数学 T-01～T-10、UI §11 逐项签核；整理 `README.md`（功能、限制、开发命令）、必要的版权与非官方声明、运行环境说明。
2. **本地构建验证**：清洁安装（适用时 `npm ci`）、运行 lint / 类型检查 / 测试 / build；用 `npm run preview` 查看生产构建版（不是只测 Vite 开发服务器）。
3. **GitHub**：由用户决定仓库公开/私有；检查 `.gitignore` 和待提交内容；**征得用户同意**后才创建/关联远程仓库、push；可按需加入 GitHub Actions 执行检查。
4. **Cloudflare Pages**：用户授权登录与连接仓库后，设置 Git 集成；通常使用构建命令 `npm run build`、输出目录 `dist`，Node 版本和依赖以项目锁文件/平台实际构建日志为准；不配置后端 Functions、不接入数据库。
5. **上线回归**：访问实际 `*.pages.dev` 地址，验证加载、3页导航、7/10抽、概率、设置保存、刷新、不同屏宽和非官方声明。移动端首次访问如国内跨境网络缓慢属于平台/网络问题，不应误判为算法问题。
6. **版本记录与回滚**：标注 `v1.0.0`（由用户决定是否打 tag），保存部署对应 commit、上线网址与回滚方法；后续改动先经测试再发布。

**验收**：真实网站链接可访问；全部关键功能在生产构建中工作；本地数据不会因为刷新丢失（用户清站点数据除外）；零服务端依赖；用户确认发布。

**明确禁止**：未经用户明确指示，不得自行购买域名、绑定银行卡、升级付费套餐、公开私人仓库或推送代码。部署平台的后台操作可能需要用户亲自完成。

## 5. 最终人工验收清单（给不熟悉前端开发的用户）

上线前可以不用看代码，按下面的真实操作验证：

1. **正常初始态**：打开计算页，选择「传说武器转盘」→ 十等奖等奖品显示正确；下一抽3卡，全部10件奖品概率都出现。
2. **国服实测例子**：点击六等奖与七等奖 → 第3抽、此前8卡、本轮10卡、二等奖 `1.497%`，等效成本 `668.000` 卡。
3. **切换类型**：从传说武器切到同为888卡总价的传说载具+武器，检查第8抽不同价格（130 与150），不能因总价相同而混淆。
4. **七抽验证**：切换七抽，点击七等奖（初始60%）→ 第2抽二等奖 `3.125%`，本轮7卡，等效成本 `224.000` 卡。
5. **设置保存**：修改某类二等奖概率（同时调整其他权重确保总和100）但不保存 → 主页面结果不变；保存后 → 主页面更新；刷新 → 新值仍在。
6. **设置恢复**：点「恢复当前默认概率」但不保存 → 仍使用旧值；点击保存 → 恢复出厂值；取消修改只放弃草稿。
7. **末轮**：标记到只剩一件正权重奖品 → `100.000%`；全部抽完 → “已完成”，没有不存在的下一抽。
8. **规则说明**：打开规则页，切换七抽/十抽示例、展开 FAQ；返回后原转盘状态不变。
9. **手机体验**：在窄屏查看所有剩余奖品、编辑每轮价格、找到保存按钮；整个页面无需横向缩放（只允许宽表内部横向滚动）。
10. **异常情况**：尝试概率总和99%、负价格、空价格 → 不得保存无效配置，不得出现“已保存”假成功。

此清单补充自动测试，但**不能替代**数学规格和 PRD 中更完整的验收条目。
