# CODM 转盘概率与成本计算器 — 数学与计算规格（PROBABILITY_SPEC）

- **版本**：v0.1（2026-11-17，首版开发基准）
- **项目**：`codm-calculator`
- **配套文档**：`docs/PRD.md`（产品需求 v0.2）
- **适用范围**：首版 **7 抽 / 10 抽** 转盘；8 种默认价格类型；任意已抽奖品集合下的**下一抽**概率、当前单轮性价比与成本。
- **实现原则**：纯本地计算；概率逻辑与 React 页面分离；不依赖网络、游戏账号或游戏服务器。

> **范围锁定**：首版仅分析**当前真实奖池状态**。自动枚举未来全部抽奖路径、截至未来某轮的累计中奖率、直到抽中目标奖品的真实期望花费、模拟抽奖、折扣与人民币换算，**均非首版必做**，留待后续扩展。以下“每 100% 概率等效卡片数”不是期望总花费或保底费用。

## 1. 术语与核心约定

| 术语 | 定义 |
|---|---|
| 转盘类型（`typeId`） | 一种独立配置，包括奖品数量、初始权重、逐抽价格、单位、奖品名称及已抽状态。首版有 8 种。 |
| 奖品（`prizeId`） | 转盘内具有稳定 ID 的单个奖品。用 ID 判断已抽状态，不以可编辑名称做索引。 |
| 初始权重（`weightPercent`） | 设置页录入的初始概率数值，单位为**百分比**，例如 `1.25` 表示 `1.25%`，不是 `0.0125`。 |
| 已抽集合（`drawnIds`） | 当前转盘已获得、从奖池剔除的奖品 ID 集合；没有重复元素。 |
| 剩余集合（`remainingIds`） | 当前转盘全部奖品 ID 减去 `drawnIds`。 |
| 已抽次数 `k` | `drawnIds.size`，范围 `0…N`。不要求知道已抽奖品的先后顺序。 |
| 下一抽轮次 `r` | 若 `k < N`，则 `r = k + 1`，范围 `1…N`；若 `k = N`，不存在下一抽。 |
| 下一抽条件概率 `p_i` | 给定当前已抽集合后，**下一抽**抽到剩余奖品 `i` 的概率，计算时采用 `0…1` 小数。 |
| 当前抽奖单轮成本 `c_r` | 第 `r` 抽需要的卡片/CP 数量，取自当前 `typeId` 的价格数组；与抽中哪件奖品无关。 |
| 单轮等效成本 `e_i` | `c_r / p_i`；仅用于比较当前这一抽的概率与成本。 |

**重要区分**：`0.08%`、`0.08`（以百分比录入的权重）、`0.0008`（以概率小数表示）是同一数值的不同表示。计算公式和代码变量命名必须明确单位，杜绝重复除以/乘以 100。

## 2. 内置默认数据

### 2.1 十抽（7 种价格类型共用的出厂初始权重）

按**一等奖 → 十等奖**顺序，单位 `%`：

```text
[0.08, 1.25, 4.00, 4.67, 5.50, 6.50, 10.00, 11.00, 28.00, 29.00]
```

合计：`100.00%`。7 种十抽类型的**出厂**权重相同，但自定义后应各自独立，不得联动覆盖。

### 2.2 七抽（通用类型的出厂初始权重）

按**一等奖 → 七等奖**顺序，单位 `%`：

```text
[0.08, 1.25, 6.67, 7.50, 8.50, 16.00, 60.00]
```

合计：`100.00%`。

### 2.3 八种类型的逐抽价格（出厂默认）

单位：首版默认显示为「使命卡片」，允许每种类型自行修改单位标签（例如 CP），**不得将不同单位自动换算**。数组顺序就是第 1 抽到最后一抽。

| 转盘类型 | 轮次价格数组 | 总计 |
|---|---|---:|
| 传说载具转盘 | `[3,5,10,20,30,50,60,90,110,160]` | **538** |
| 传说近战转盘 | `[3,5,10,20,30,50,60,90,110,160]` | **538** |
| 传说载具+武器转盘 | `[3,5,10,20,40,60,90,150,160,350]` | **888** |
| 传说武器转盘 | `[3,5,10,20,40,60,90,130,180,350]` | **888** |
| 神话武器转盘 | `[3,5,10,20,40,60,90,150,210,420]` | **1008** |
| 传说角色转盘 | `[3,5,10,20,40,60,90,130,230,420]` | **1008** |
| 神话角色转盘 | `[5,8,15,30,60,90,130,210,350,550]` | **1448** |
| 七抽转盘（通用） | `[3,7,18,50,90,180,350]` | **698** |

- 十抽必须有 **10** 个奖品权重、**10** 个价格；七抽必须有 **7** 个权重、**7** 个价格。
- 七抽设置表第 8～10 抽为**不适用**，而非价格为 `0` 的三轮。
- 每种类型存储独立的权重、价格、名称、单位和已抽状态。即使总价相同，也不得合并价格数组。
- 上述数据为用户确认的项目**默认模板**；特殊活动或不同服务器若有不同公示，以用户设置为准。

## 3. 概率计算：固定权重、剔除后归一化

### 3.1 状态与输入

对于某个转盘，令：

- `N`：奖品数量（7 或 10）。
- `w_i`：奖品 `i` 的初始权重，使用设置页输入的百分比数值；要求 `w_i >= 0`。
- `D`：已抽奖品集合；`R`：未抽奖品集合。
- `W_R = Σ_(j∈R) w_j`：当前剩余权重总和。

### 3.2 核心公式

只要 `W_R > 0`，对每个**未抽中**奖品 `i ∈ R`：

\[
p_i = \frac{w_i}{W_R}\quad\text{（概率小数）}
\]

\[
P_i(\%) = 100\times\frac{w_i}{W_R}\quad\text{（用于显示的百分比）}
\]

对 `i ∈ D`：不再参与抽取；UI 显示「已抽取」，不显示为仍可中奖的条目。程序可以使用 `null`/状态标记表示“已剔除”，不要将“已抽取”与“尚未抽中但权重为 0”混为一谈。

**重要性质**：概率只由当前**剩余集合**决定，与前面抽中的顺序无关。不允许将十抽默认奖品理解为“按权重由大到小固定出货”。

### 3.3 状态变化

1. 选择一种转盘类型，加载该类型的**有效配置**和已抽状态。
2. 用户勾选/取消勾选一个已抽奖品 ID；形成新的 `D`。
3. 自动令 `k = |D|`，若 `k < N` 则 `r = k + 1`。
4. 计算 `R`、`W_R`、每个 `p_i`、本轮价格及性价比，并立即刷新页面。
5. 切换转盘类型不改变其他类型的 `D`、价格、权重。
6. 如 UI 提供单独的轮次选择器，必须与 `k + 1` 保持一致；不允许“轮次显示第 5 抽、实际上只剔除两件”仍输出有效结果。推荐使用已抽数量自动决定轮次。

### 3.4 不变量（自动化测试必须验证）

- `0 <= |D| <= N`，`R` 与 `D` 不重叠，且二者合计恰好覆盖 `N` 件奖品。
- 对 `W_R > 0` 的有效状态：每个 `p_i ∈ [0,1]`；所有未抽奖品 `Σ p_i = 1`（**内部精度**允许浮点误差 `1e-10`）。
- 对同一已抽集合，无论选择顺序如何，输出完全相同（数值在浮点容差内相等）。
- 不改变价格/显示名称的条件下，修改已抽集合只影响概率和当前轮次，不改变原始权重。
- 价格配置只影响价格和单轮等效成本，**绝不影响概率**。

## 4. 单轮性价比：每 100% 概率的等效卡片数

对于当前下一抽的任意剩余奖品 `i`，当前该轮成本 `c_r`，其下一抽中奖概率小数 `p_i`：

\[
e_i = \frac{c_r}{p_i}\qquad (p_i>0)
\]

界面标签必须使用：**「本轮每 100% 中奖概率等效卡片数」**（或保持语义完全一致的简短标签），单位与当前价格一致。

例如：第 1 抽消耗 `3` 张，二等奖 `p = 0.0125`，则 `e = 3 / 0.0125 = 240.000` 张。

- **数值越低**，表示在当前**这一抽**中获得单位概率所花费的卡片越少。
- 它是**单轮成本/概率指标**，并**不等于**连续抽到某奖品的期望总投入、保底费用或可实际兑换价格。结果区与帮助页均须注明。
- 可在 UI 后续另加「每 1 个百分点概率成本」，但首版**主指标仅要求每 100% 概率等效卡片数**，避免把 `c_r / p_i` 和 `c_r / P_i(%)` 混淆。
- 若 `p_i = 0`：显示**「当前不可抽中」或「不适用」**，不得除以 0，亦不得显示为 `0` 张或正常性价比数字。
- 若该轮价格缺失/非法：概率照常计算，性价比显示「待设置价格」；**不得把空价格当 0**。
- 若用户明确设置 `c_r = 0` 且 `p_i > 0`：`e_i = 0.000`，这是合法的免费抽奖状态。

## 5. 花费计算与显示

令当前已抽 `k` 次、下一抽轮次 `r=k+1`、该类型逐抽成本为 `c_1,…,c_N`。使用该类型当前生效的价格配置：

\[
\text{此前已花费 } S_{\text{paid}}(k)=\sum_{t=1}^{k}c_t
\]

\[
\text{本轮需要 } C_{\text{next}} = c_{k+1}\qquad(k<N)
\]

\[
\text{完成本轮后累计 } S_{\text{after}}(k)=\sum_{t=1}^{k+1}c_t\qquad(k<N)
\]

\[
\text{全抽保底总成本 } S_{\text{full}}=\sum_{t=1}^{N}c_t
\]

- `k=0` 时，此前已花费为 **0**。
- `k=N` 时，**不存在下一抽**；此前累计 = 全抽总成本，本轮费用、完成本轮后累计、概率和性价比均为「—／已完成」，不再取 `c_(N+1)`。
- 不使用用户实际中奖的奖品等级来改变第 `r` 抽价格；只根据已抽次数取价格数组。
- 如某轮已发生的价格被用户修改，可按**当前价格配置**重新展示理论累计费用；首版不提供逐轮真实支付记录。界面或帮助页应明确为“按当前配置计算”。
- 对价格数据不完整的处理：能从**已知价位**计算的字段可保留；凡依赖未配置价位的合计字段都应标注「价格不完整」而非偷偷补 0。概率始终可独立显示。

## 6. 边界条件与输入校验

### 6.1 概率权重输入

- 接受有限数值且 `w_i >= 0`（允许 `0`），不得为 `NaN`、`Infinity`、负数或空字符串。
- 奖品数量必须与转盘类型一致，奖品 ID 唯一，不能缺少奖品。
- 初始权重总计应为 **100%**；考虑浮点误差，判定容差：`abs(sum(weights) - 100) <= 1e-6`（单位：**百分点**），不应使用界面已舍入的值作校验。
- 如总计不符合要求，提示实际合计与偏差，并**阻止该无效权重配置参与正式计算**；不允许静默将明显错误的权重归一化、冒充合法的官方概率。
- 由于允许单项权重为 0，必须至少有一个正权重；如果用户选出的剩余奖品全部 `w=0`，则 `W_R=0`，状态**不可计算**：提示「剩余奖品总权重为0，请检查概率设置或已抽奖品」，不得返回 `NaN`、`Infinity`、空白伪装成 100%。
- 若用户把初始概率为 0 的奖品标记为“已抽”，这与当前模型不符；建议给予提示“当前配置下此奖品不可能被抽到”，而不是默默认作正常概率路径。可允许用户改回权重或撤销勾选。

### 6.2 价格输入

- 每轮价格为**有限、非负整数**；`0` 合法（免费抽），空白不等于 `0`。
- 价格数组长度必须严格等于 `N`；七抽不得生成第 8～10 抽。
- 对非法或不完整价格，不输出貌似有效的总计与性价比；应显示校验提示。概率仍可用。
- 价格单位为每种类型的标签，首版不进行跨单位或人民币换算。

### 6.3 已抽状态

- `drawnIds` 必须全部是当前类型有效奖品 ID；无重复、超限或跨类型混入。
- 已抽状态因切换类型独立保存；重置某类型只清空该类型 `drawnIds`。
- 配置或奖品 ID 发生结构变化时，须校验并清理不再存在的 ID；首版默认奖品数量固定为 7 或 10。
- 用户编辑概率或价格后，应即时重新计算；无效设置不能覆盖最后一份有效持久化配置（或须以清晰错误状态阻止使用），由 Codex 选择一致的表单实现策略。

### 6.4 最后一抽与全部抽完

- 当 `|R| = 1` 且唯一剩余奖品的权重 **大于 0** 时，它的下一抽概率精确为 `1`，显示 **`100.000%`**；等效成本等于该轮价格，显示 `c_N.000`。
- 当 `|D| = N` 时，不存在下一抽；显示「转盘已全部抽完」，此前累计 = 总成本，不显示下一轮概率、性价比或价格。
- **例外**：如果最后一个奖品权重为 `0`，不应因为“只剩一件”就强行写成 `100.000%`；按 `W_R=0` 的非法/不可计算状态处理。

## 7. 数值精度与格式

1. **计算精度**：在内部保留 JavaScript/TypeScript `number` 的计算精度，不得先用 `.toFixed(3)` 的结果继续参与计算。
2. **显示精度**：
   - 当前下一抽中奖概率：固定保留 **3 位小数**，例如 `1.497%`、`100.000%`。
   - 每 100% 概率等效成本：固定保留 **3 位小数**，例如 `668.000 张`。
   - 单轮卡片、此前累计、完成本轮累计、总价：**整数**（例如 `10 张`、`888 张`）。
3. **舍入规则**：**四舍五入**至小数点后三位（正数在精确半值处向上），不要截断；全部已抽/不适用/缺价状态应显示文字或 `—`，不显示零值冒充有效结果。
4. **已显示概率总和**：由于逐项四舍五入，页面上的各奖品数字之和可能是 `99.999%` 或 `100.001%`；以内部未舍入的概率合计约 `100%` 为准，**不得为了凑显示 100% 擅自修改某一奖品概率**。
5. **极小正概率**：如自定义权重导致正概率显示为 `0.000%`，不得在计算中把它置零；建议用辅助提示「原始概率大于0，仅因显示精度舍入为0.000%」，防止被误读为不可能中奖。
6. **测试容差**：核心公式比较使用浮点容差；页面字符串比较使用明确的三位小数格式。

## 8. 建议的数据结构与纯函数接口（供 Codex 实现参考）

以下只约束**数学语义与字段关系**，具体文件名和 TypeScript 类型实现可在开发计划阶段调整。

```ts
interface Prize {
  id: string;              // 稳定ID，例如 prize_1
  name: string;            // 可修改的显示名称
  weightPercent: number;   // 百分数，例如 1.25 表示 1.25%
}

interface DrawPreset {
  typeId: string;          // 如 legendary_weapon、seven_draw
  label: string;
  prizes: Prize[];         // 长度 7 或 10
  roundCosts: number[];    // 同长度，依次是第1...第N抽
  currencyLabel: string;   // 使命卡片 / CP 等
}

interface DrawState {
  typeId: string;
  drawnIds: string[];      // 在逻辑层当作集合处理
}

interface PrizeResult {
  prizeId: string;
  status: 'remaining' | 'drawn';
  probability: number | null; // 0..1；已抽取时null
  equivalentCost: number | null; // 缺价、已抽取、p=0时null并单独给出原因
}
```

建议将算法实现为**无副作用纯函数**：

- `validateWeights(prizes)`：验证数值、数量/ID及总和（数量也可由外层校验）。
- `getNextRound(drawnIds, N)`：返回 `k+1` 或完成状态。
- `calculateRemainingProbabilities(prizes, drawnIds)`：返回当前概率或明确的验证错误；不读写浏览器存储。
- `calculateCosts(roundCosts, k)`：返回本轮、此前、完成本轮后与全抽费用；处理未配置价格。
- `calculateEquivalentCosts(probabilities, nextRoundCost)`：返回每件剩余奖品的单轮等效成本；避免除 0。
- `formatDisplayValue(...)`：**仅在展示层**应用三位小数与四舍五入规则。

不要把 React 状态、`localStorage`/IndexedDB 或动画代码混入核心概率函数。为了未来 Capacitor/离线 APK 复用，概率计算不得依赖浏览器全局对象或网络接口。

## 9. 必须通过的验收测试（含明确数值）

以下用例中的中奖概率、等效成本显示均按**三位小数**；内部概率总和检查单独采用浮点容差。

### T-01：两种默认概率总和

- 十抽 10 个权重合计 `100.00%`；七抽 7 个权重合计 `100.00%`。
- 初始未抽时：十抽一等奖 `0.080%`、二等奖 `1.250%`；七抽同样如此。

### T-02：十抽剔除六等奖和七等奖

- 选十抽标准权重，已抽走权重 `6.50%` 与 `10.00%` 两件奖品，`k=2`、下一抽 `r=3`。
- 当前剩余权重：`83.50`。
- 一等奖：`0.08 / 83.5 × 100 = 0.095808...%` → **`0.096%`**。
- 二等奖：`1.25 / 83.5 × 100 = 1.497005...%` → **`1.497%`**。
- 权重 `29%` 的奖品：`29 / 83.5 × 100 = 34.730538...%` → **`34.731%`**。
- 若该转盘第 3 抽价格 `10` 张：二等奖等效成本 `10 / (1.25/83.5)` → **`668.000` 张**；一等奖为 **`10437.500` 张**。
- 本轮 `10` 张；此前累计 `3+5=8` 张；完成本轮累计 `18` 张。

### T-03：十抽只剔除最大权重奖品

- 先抽掉 `29%` 奖品：剩余权重 `71`，第 2 抽二等奖为 `1.25/71×100 = 1.760563...%` → **`1.761%`**。
- 改为只抽掉 `28%` 奖品：剩余权重 `72`，二等奖为 `1.25/72×100 = 1.736111...%` → **`1.736%`**。
- 证明同一轮次的概率**取决于实际已抽奖品**，不能按轮次写死。

### T-04：七抽先剔除 60% 奖品

- 选七抽，已抽走 `60.00%` 奖品，下一抽 `r=2`，剩余权重 `40`。
- 一等奖：`0.08/40×100 = 0.200%`。
- 二等奖：`1.25/40×100 = 3.125%`。
- 三等奖：`6.67/40×100 = 16.675%`。
- 第 2 抽价格：`7` 张；此前累计：`3` 张；完成本轮累计：`10` 张。
- 二等奖等效成本：`7 / 0.03125 = 224.000` 张。

### T-05：状态顺序无关

- 十抽：先剔除 `6.5%` 再剔除 `10%` 与先剔除 `10%` 再剔除 `6.5%`，下一抽所有概率完全一致（容差 `1e-10`），轮次都是 `3`。

### T-06：不同转盘价格不可混用

- 「传说武器转盘」第 8 抽为 **130** 张；「传说载具+武器转盘」第 8 抽为 **150** 张，虽二者总价都为 **888**。
- 「神话角色转盘」第 1 抽为 **5** 张，而常见十抽的第 1 抽为 **3** 张。
- 七抽第 3 抽为 **18** 张、此前 **10** 张、完成后 **28** 张、全部 **698** 张。
- 八种默认配置总价逐一验证为 `538, 538, 888, 888, 1008, 1008, 1448, 698`。

### T-07：第 1 抽的二等奖性价比

- 初始二等奖 `1.250%`，第 1 抽成本 `3` 张，等效成本 `3 / 0.0125 = 240.000` 张。
- 在「神话角色转盘」第 1 抽成本 `5` 张时，同概率下等效成本 `400.000` 张。

### T-08：最后一抽与已完成

- 十抽仅剩一个**正权重**奖品时：显示 `100.000%`，本轮成本取第 10 抽；若选传说武器转盘，价格为 `350`，等效成本 **`350.000`** 张，此前累计 **`538`** 张，完成本轮累计 **`888`** 张。
- 七抽仅剩一个正权重奖品时：第 7 抽 `350` 张，已花 **`348`** 张，完成后 **`698`** 张，等效成本 **`350.000`** 张。
- 全部奖品均已抽走时，显示「转盘已全部抽完」，无第 `N+1` 抽和无下一轮概率。

### T-09：非法与特殊数值

- 负概率、`NaN`、`Infinity`、权重总和偏离 100 超出容差 → 阻止正式计算，给出明确错误。
- 若剩余集合总权重 `0` → 不得自动返回 100%。
- 某个剩余奖品权重为 `0`、另有正权重奖品 → 该奖品概率 **`0.000%`**，但其等效成本显示「当前不可抽中」，不进行除零。
- 单轮价格缺失 → 概率正常显示；该轮等效成本为「待设置价格」。
- 单轮价格真实设为 `0` → 允许并正确显示等效成本 `0.000`。
- 已抽奖品数量、转盘类型、奖品 ID 不一致 → 阻止计算或安全校正并告知用户，不可静默带入其他奖池。

### T-10：格式与精度

- `0.095808...%` → `0.096%`；`1.497005...%` → `1.497%`；`100%` → `100.000%`。
- `668` 等效成本 → `668.000`；真实单轮价格 `10` → `10`（不加小数）。
- 不使用已显示的 `1.497%` 反向计算等效成本，必须使用未舍入的 `1.25/83.5`。
- 仅展示层舍入；全部剩余概率在内部合计为 `1`（容差内）。

## 10. 开发完成的判定标准

Codex 交付首版数学模块时，必须满足：

1. **自动化测试**覆盖本规格 §9 的全部用例；测试结果可以在本地通过 npm 命令重现。
2. 计算模块可单独导入、独立测试，不需要打开页面，也不依赖网络。
3. 页面上清楚区分「初始概率」「当前下一抽真实概率」「本轮花费」「此前累计」「完成本轮后累计」「全抽总计」「每100%概率等效成本」。
4. 所有概率和性价比**展示三位小数、四舍五入**；价格展示整数；算法内部不提前舍入。
5. UI 有醒目的简短解释：**“等效卡片数仅用于比较本轮性价比，并非实际保底价格或期望总花费。”**
6. 八种转盘默认配置准确、独立编辑及重置，7/10 抽状态不混淆。
7. 未实现的高级预测功能不应在 UI 中误写为已具备；未来扩展留独立接口即可，不预先做复杂的路径枚举。
